Build with PBreeze.

A complete, practical guide to the native PHP framework. Start with a working feature, then keep the function reference beside you.

    For PHP 8.3+ on Windows and Linux. No Composer, no PSR autoloading, and no external PHP packages. All maintained explanations and examples are US English. This manual opens directly from disk and works offline; JavaScript only enhances search and printing.

    Coverage: 47 framework classes, 239 declared public methods and protected relationship helpers, 2 global helpers, all CLI commands, and every example environment setting.

    How to use this manual

    1. Follow Build your first feature for a complete route, validation, database, and view workflow.
    2. Use the chapters for full feature guides and production limits.
    3. Use the function reference for exact signatures, parameter defaults, return types, and simple examples.

    Examples are learning material, not commands to run blindly against production. Replace example IDs, domains, and owner checks with application-specific values. Back up before schema changes.

    Build your first feature

    This walkthrough builds a small notes screen using a fresh local PBreeze installation. It reuses the shipped notes migration. All paths below are relative to the project root. Use a disposable development database while learning.

    Check PHP and initialize

    Open a terminal in the project folder. On Windows, use PowerShell or cmd; on Linux, use your normal terminal. Install PHP 8.3+ and enable the native extensions listed in Getting Started. There is no Composer install step.

    php -v
php -m
php breeze init
php breeze migrate
php breeze migrate:status

    init preserves an existing .env. Inspect that file before migrating. The default local database is SQLite at database/app.sqlite; migrations create the notes, email, authentication, and API tables. migrate:status shows applied batches.

    Understand where code runs

    public/index.php boots the framework and returns an Application. routes/web.php explicitly imports controllers and registers handlers. Controllers receive a Request and return a Response. Templates render display content; database queries belong in controllers/models, not HTML.

    Use $app->db, $app->views, and other injected services. Never create an autoloader or rely on magic class discovery. A controller existing on disk does not make it public: only a registered route does.

    Create a controller

    php breeze make:controller NotebookController

    Replace the generated controller body with this small example in app/controllers/NotebookController.php. The constructor explicitly receives Application. The GET action reads twenty notes; the POST action validates and inserts only a title.

    <?php
declare(strict_types=1);

namespace App\Controllers;

use PBreeze\Application;
use PBreeze\Request;
use PBreeze\Response;
use PBreeze\Validator;

final class NotebookController
{
    public function __construct(private readonly Application $app) {}

    public function index(Request $request): Response
    {
        return $this->page();
    }

    public function store(Request $request): Response
    {
        $errors = Validator::errors($request->all(), [
            'title' => 'required|string|min:2|max:120',
        ]);
        if ($errors !== []) {
            return $this->page($errors, 422);
        }
        $this->app->db->table('notes')->insert([
            'title' => $request->input('title'),
            'created_at' => gmdate('Y-m-d H:i:s'),
        ]);
        return Response::redirect('/notebook');
    }

    private function page(array $errors = [], int $status = 200): Response
    {
        return new Response($this->app->views->render('notebook.index', [
            'notes' => $this->app->db->table('notes')
                ->orderBy('id', 'desc')->limit(20)->get(),
            'errors' => $errors,
            'session' => $this->app->session,
        ]), $status);
    }
}

    On success, the browser receives a 303 redirect, so refreshing the notes page does not repeat the insert. On invalid input, the handler returns the same page with status 422 and visible errors. The query builder binds the title value instead of concatenating SQL.

    Register the routes explicitly

    Append these lines to routes/web.php. Keep existing routes intact. This is a local learning feature with shared notes, not a multi-user authorization design.

    require_once $app->root . '/app/controllers/NotebookController.php';
$notebook = new \App\Controllers\NotebookController($app);
$router->get('/notebook', [$notebook, 'index']);
$router->post('/notebook', [$notebook, 'store']);

    Create the view

    php breeze make:template notebook.index

    Replace the generated content in app/views/notebook/index.breeze.php with the following. {{ ... }} escapes text; @csrf($session) supplies the hidden token. Unlike raw output, the escaped title cannot introduce executable HTML.

    <!doctype html>
<html lang="en-US">
<head><meta charset="utf-8"><title>My notebook</title></head>
<body>
    <h1>My notebook</h1>
    @if(!empty($errors))
        <p role="alert">{{ implode(' ', $errors['title'] ?? []) }}</p>
    @endif
    <form method="post" action="/notebook">
        @csrf($session)
        <label for="title">Note title</label>
        <input id="title" name="title" required minlength="2" maxlength="120">
        <button type="submit">Save note</button>
    </form>
    <ul>
        @foreach($notes as $note)
            <li>{{ $note['title'] }}</li>
        @endforeach
    </ul>
</body>
</html>

    Run and check the feature

    php breeze routes
php breeze serve

    Open http://127.0.0.1:8000/notebook. Save a note, then try a one-character title. The valid note should appear; invalid input should show an error without inserting a row. Missing CSRF should return 419. Stop the development server before running another process on the same port.

    Move from demo to application

    Wrap both handlers with $app->auth->protect(...) if login is required. Add a new migration for a note-owner column and scope every read/write to the authenticated owner. The guard checks identity/verification, not object ownership. For public forms, also integrate the purpose-bound CAPTCHA/honeypot workflow from its chapter. Do not deploy the unscoped learning feature as a private notebook.

    $router->get('/notebook', $app->auth->protect([$notebook, 'index']));
$router->post('/notebook', $app->auth->protect([$notebook, 'store']));

    Use these guarded registrations instead of the unguarded ones, not in addition. The existing registration/login/verification pages are already wired; configure mail and run a worker so verification/reset emails can be delivered.

    Common service recipes

    // Display an exact amount without using floating-point money.
$total = $app->format->money('1234.565', 'USD'); // $1,234.57

// Create a JSON export; authorize access before returning it.
$file = \PBreeze\Documents\Documents::json(['total_display' => $total]);
$response = $file->download('summary.json');

// Log safe identifiers, not request bodies, passwords, or tokens.
$app->log->info('Summary created.', ['report_id' => 42]);

// Build and queue an email; delivery is a separate worker action.
$message = $app->mail->compose([
    'to' => ['ada@example.test'],
    'subject' => 'Your summary is ready',
    'text' => 'Sign in to view your summary.',
]);
$emailId = $app->mail->queue($message);

    These recipes illustrate separate tasks; do not queue mail while rendering a GET page. Perform side effects only in an authorized, validated action and use the queue worker deliberately.

    Every CLI command

    Run from the project root with php breeze on Windows or Linux. Names are arguments, not arbitrary paths. Generators reject traversal, invalid identifiers, Windows device names, and existing/conflicting output rather than overwriting work.

    Commands normally return exit status 0 on success; failures print an error and exit nonzero. Commands can create files, change the database, or send actual email. --force permits production migrations/rollback/seeding; it is not a universal overwrite switch. API commands do not accept it.

    init

    Create .env from .env.example only if absent, with private platform-appropriate permissions. Existing configuration is preserved; no database or application key is created.

    php breeze init

    key:generate

    Print a fresh APP_KEY assignment. Copy it securely to .env yourself; files are not changed. Replacing a key makes older encrypted data unreadable unless you plan a migration.

    php breeze key:generate

    serve

    Start the native localhost development server, default port 8000, or a supplied 1024..65535 port. Runs in the foreground until stopped. Never use as a production server.

    php breeze serve 8080

    routes

    Load web/API route registries and print method/path pairs. Duplicate imports or invalid routes fail rather than being ignored.

    php breeze routes

    make:controller

    Create a controller skeleton under app/controllers. Explicitly require it and register its actions in routes/web.php; generating a controller does not expose a URL.

    php breeze make:controller ContactController

    make:api

    Create API controller, route module, explicit registry import, and OpenAPI metadata together. Default resource actions are bearer-protected 501 placeholders; implement authorization and actual persistence before use.

    php breeze make:api Products

    api:token

    Issue a bearer token for an existing verified user. Optional name defaults to cli; days defaults to 30 and accepts 1..365. The secret is printed once: do not log/share it or paste it into source control.

    php breeze api:token 1 integration 30

    api:tokens

    List token metadata for the supplied user ID, not token secrets. Use IDs from this list to revoke a token.

    php breeze api:tokens 1

    api:revoke

    Revoke the token identified by its token-row ID, not user ID. Already-issued clients will subsequently receive unauthorized responses.

    php breeze api:revoke 12

    api:openapi

    Print the registered OpenAPI JSON document to stdout. This still works with public API docs disabled. Shell redirection creates a file; keep export paths trusted.

    php breeze api:openapi

    make:model

    Create an explicitly loaded Model subclass under app/models. Configure the correct table, fillable, hidden, and casts before using it. It does not create or alter a database table.

    php breeze make:model Article

    make:view

    Create a plain PHP view using a dot-separated name. Render it through View, escaping values with e(); no route is registered.

    php breeze make:view articles.index

    make:template

    Create a compiled Breeze .breeze.php source template. The first render compiles it into storage/views. No Node/npm build or route registration is needed.

    php breeze make:template articles.index

    view:clear

    Remove recognized compiled Breeze cache files and print the count. Source views remain untouched; subsequent renders compile again.

    php breeze view:clear

    make:migration

    Create a timestamped migration with up/down methods. Fill in driver-appropriate schema SQL before migrating; generation itself does not connect or change schema.

    php breeze make:migration create_articles

    make:seeder

    Create a seeder under database/seeders. Write repeatable inserts/updates deliberately. Seeders are executable trusted PHP, not validated user input.

    php breeze make:seeder ArticleSeeder

    migrate

    Apply pending migrations in order and print applied names. Production requires --force after a backup. SQLite DDL is transactional; MySQL DDL may not roll back.

    php breeze migrate

    migrate:status

    Print OPEN or BATCH numbers for discovered migrations, helping distinguish pending/applied schema work. Missing applied migration files are treated as errors.

    php breeze migrate:status

    migrate:rollback

    Run down() for only the latest batch in reverse order. May destroy data; production requires --force. Rollback is not a substitute for a backup.

    php breeze migrate:rollback

    db:seed

    Run the named seeder, or DatabaseSeeder when omitted. Production requires --force. Review the seeder first because it can change/delete data.

    php breeze db:seed ArticleSeeder

    mail:queue

    Read an existing JSON object file up to 6 MiB, validate from/to/subject/text/html, store a queued message, and print its ID. No SMTP is sent by this command.

    php breeze mail:queue message.json

    mail:list

    Print recent email metadata as JSON; default 50, accepted range 1..1000. Bodies are not listed, but subjects and delivery diagnostics can still be confidential.

    php breeze mail:list 20

    mail:show

    Print a complete stored email row as JSON by positive ID. Contains private message content; restrict terminal output, logs, and access.

    php breeze mail:show 12

    mail:send

    Claim/send one queued outgoing ID using SMTP, update its status, and report acceptance. Acceptance is not inbox delivery. Failed/uncertain rows require explicit retry handling first.

    php breeze mail:send 12

    mail:work

    Send queued IDs oldest-first in one bounded run, default 50, accepted 1..1000. Stop at the first failure. This is not a persistent daemon; schedule it with cron/Task Scheduler.

    php breeze mail:work 50

    mail:retry

    Requeue failed outgoing mail. --force also permits uncertain/sending recovery, which can duplicate delivery; stop active workers and check SMTP evidence first.

    php breeze mail:retry 12

    mail:fetch

    Read/import up to 1..1000 IMAP messages, default 50, without marking Seen or changing the mailbox. MAIL_LOG controls database import/deduplication.

    php breeze mail:fetch 10

    test

    Run isolated native tests, local HTTP, SQLite, and local SMTP/IMAP fixtures. No external email is sent. Requires process/socket support and documented extensions.

    php breeze test

    help

    Print usage and the complete current command list. Also the default when no command is supplied. Unknown commands/options and excess arguments fail explicitly.

    php breeze help

    JSON input for mail:queue

    Create message.json yourself with a recipient list and at least one body. The configured MAIL_FROM is used when from is omitted. Do not commit real private message content.

    {
    "to": ["ada@example.test"],
    "subject": "Welcome",
    "text": "Hello, Ada!"
}

    For a reviewed production migration, the explicit form is php breeze migrate --force. For an investigated uncertain email, php breeze mail:retry 12 --force can requeue it, but may duplicate delivery. Never combine either with an unreviewed deployment script.

    Environment reference

    The following defaults/example values come from the committed .env.example, never from a developer's real .env. System environment variables override the file. An empty value is not the same as a missing variable. Quotes remove only their outer delimiters; inline comments, interpolation, multiline values, and escape processing are unsupported.

    APP_NAME

    Example file value: PBreeze

    Application name used in pages and API metadata. Default PBreeze.

    LOG_RETENTION_DAYS

    Example file value: 5

    Daily-file retention window, 1..3650 days, default 5. Includes today; pruning runs when an entry is written.

    LOG_LEVEL

    Example file value: debug

    Minimum lowercase severity: debug, info, notice, warning, error, critical, alert, emergency. Default debug. Higher thresholds may filter automatic error entries.

    UPLOAD_MAX_BYTES

    Example file value: 2097152

    Positive integer per-file default for the Uploads service, default 2097152 (2 MiB). Does not change PHP or proxy request limits; handlers can override.

    APP_LOCALE

    Example file value: en-US

    Default display locale for Formatter, en-US. Does not translate framework-maintained UI. Process environment overrides .env.

    APP_TIMEZONE

    Example file value: UTC

    Default Formatter IANA zone, UTC. No global PHP timezone change occurs.

    APP_URL

    Example file value: http://127.0.0.1:8000

    Trusted base URL for authentication email links. Use the actual HTTPS origin in production; do not derive it from untrusted Host input.

    APP_ENV

    Example file value: local

    local, testing, or production only. If absent, configuration defaults to production; the example file intentionally selects local.

    APP_DEBUG

    Example file value: false

    Boolean diagnostic web output flag. Detailed errors are shown only with local environment and true. Keep false in production; API unexpected errors stay generic.

    APP_KEY

    Example file value: (empty)

    Secret base64:-prefixed 32-byte encryption key. Empty disables usable encryption, not unrelated features. Generate securely; never commit or log it.

    API_DOCS_ENABLED

    Example file value: true

    Optional boolean override. Without it, HTTP Swagger/OpenAPI is enabled in local/testing and disabled in production. Static vendored assets remain public.

    DB_CONNECTION

    Example file value: sqlite

    sqlite or mysql. Tests use disposable SQLite; live MySQL deployment requires its own integration verification.

    DB_DATABASE

    Example file value: database/app.sqlite

    SQLite file path relative to project root, absolute local path, or :memory:. For MySQL, the database name. SQLite should not use SMB/NFS shared storage.

    DB_HOST

    Example file value: 127.0.0.1

    MySQL hostname/address, default 127.0.0.1. Not used for SQLite; must meet the native DSN validation rules.

    DB_PORT

    Example file value: 3306

    MySQL port 1..65535, default 3306. Not used for SQLite.

    DB_USERNAME

    Example file value: root

    MySQL login name, default root for initial local setup. Use a least-privilege application account in production.

    DB_PASSWORD

    Example file value: (empty)

    Secret MySQL password. Empty in the example, not a production recommendation.

    SESSION_SECURE_COOKIE

    Example file value: false

    Boolean Secure-cookie flag, false locally. Set true behind a properly configured HTTPS proxy; this does not encrypt an HTTP connection by itself.

    MAIL_LOG

    Example file value: true

    Boolean immediate-send logging/IMAP-import control, default true. Explicit queue() and auth mail always use the database queue.

    MAIL_FROM

    Example file value: noreply@example.test

    Default ASCII sender without a display name. Replace example.test with a valid authorized sender before real delivery.

    SMTP_HOST

    Example file value: (empty)

    SMTP server hostname/address. Empty until configured. Do not send through arbitrary user-selected hosts.

    SMTP_PORT

    Example file value: 587

    SMTP TCP port, default 587 for STARTTLS. Use the server-authorized port matching the selected encryption mode.

    SMTP_ENCRYPTION

    Example file value: starttls

    starttls, tls, or none. Default starttls; tls starts TLS immediately. none is restricted to unauthenticated localhost.

    SMTP_USERNAME

    Example file value: (empty)

    SMTP authentication username when required. Never log credentials.

    SMTP_PASSWORD

    Example file value: (empty)

    Secret SMTP authentication password/app password. Protect .env and backups.

    SMTP_TIMEOUT

    Example file value: 15

    Native socket timeout seconds, 1..300, default 15. A timeout after DATA may leave uncertain delivery.

    SMTP_CA_FILE

    Example file value: (empty)

    Optional readable CA bundle for peer verification. Empty uses system/PHP trust. Never disable verification to work around certificate problems.

    IMAP_HOST

    Example file value: (empty)

    IMAP server hostname/address. Empty until configured.

    IMAP_PORT

    Example file value: 993

    IMAP port, default 993 for immediate TLS. Match the server configuration when using STARTTLS instead.

    IMAP_ENCRYPTION

    Example file value: tls

    tls, starttls, or restricted none. Default tls; ordinary authenticated IMAP requires encryption.

    IMAP_USERNAME

    Example file value: (empty)

    IMAP account username. Used with encrypted LOGIN; not exposed in manual output.

    IMAP_PASSWORD

    Example file value: (empty)

    Secret IMAP password/app password. Never paste it into documentation or diagnostics.

    IMAP_TIMEOUT

    Example file value: 15

    Socket timeout seconds, 1..300, default 15.

    IMAP_CA_FILE

    Example file value: (empty)

    Optional readable CA trust bundle, otherwise PHP/system CA defaults are used.

    IMAP_MAILBOX

    Example file value: INBOX

    Read-only examined mailbox, default INBOX. ASCII or IMAP modified UTF-7 name, up to 255 printable ASCII bytes.

    IMAP_MAX_BYTES

    Example file value: 10485760

    Per-message retrieval bound, 1..52428800 bytes, default 10485760 (10 MiB). Batch retrieval is also bounded at 50 MiB.

    PHP and web-server settings are separate

    upload_max_filesize, post_max_size, max_file_uploads, upload_tmp_dir, session save paths, CA certificates, memory/time limits, error logging, and web-server body/TLS limits are not automatically set from these environment keys. Configure the PHP installation used by the actual web server, which may differ from CLI PHP.

    Troubleshooting

    Class not found
    Check exact filename casing and add an explicit require_once before using the class. PBreeze intentionally has no Composer/PSR autoloader.
    404 or 405
    Run php breeze routes. Check the exact route, HTTP method, registry import, and web-server front-controller rewrite. Generating a controller/view does not automatically register it.
    419 Session verification failed
    Reload the form, keep the same session cookie, and submit the current hidden CSRF token or header. Login/logout/reset rotate session state. Multipart requests need CSRF too.
    422 Security check failed
    Use the new CAPTCHA challenge after every attempt. Keep the website honeypot empty and submit the correct form purpose within five minutes. A consumed code cannot be retried.
    401 on the API
    Use an unexpired, unrevoked bearer token for a verified user. Browser login cookies do not authenticate API requests. A password reset invalidates existing tokens.
    413 uploading
    Compare UPLOAD_MAX_BYTES, handler overrides, PHP upload_max_filesize/post_max_size, multipart overhead, and proxy limits. Framework settings cannot raise PHP/server limits.
    415 on the API
    Send an application/json object, not form data or multipart uploads. Use normal web routes for native file uploads/downloads.
    429 Too many requests
    Honor Retry-After. Direct REMOTE_ADDR is used; clients behind a reverse proxy may share its IP. Do not disable rate limits to hide an upstream configuration issue.
    Unexpected 500
    Inspect private storage/logs and PHP server logs. Automatic exception entries record safe source location/class, not messages or arguments. Verify required extensions, permissions, environment validation, and schema status.
    Missing extension
    Use php -m for CLI, and inspect the web PHP configuration separately. Enable native PDO/SQLite or MySQL, OpenSSL, iconv, mbstring as needed, Intl, zip, DOM, and fileinfo for the features/tests described. Do not install Composer packages as substitutes.
    Email stays queued
    Configure SMTP and run mail:work. Registration/reset queue mail rather than sending it inline. Check delivery status; uncertain/sending recovery can duplicate messages.
    Verification link points to localhost
    Set APP_URL to the trusted public HTTPS base URL before creating new links. Existing queued messages retain their original content.
    Encrypted content will not decrypt
    Check the exact APP_KEY and authenticated context. Never generate a replacement key to fix unreadable existing data. Restore the original key from secure backup or perform a planned migration.
    Formatting differs between machines
    Compare explicit locale/time zone and installed ICU data versions. Nonbreaking spaces, localized digits, and punctuation are intentional. Never parse formatted money as database numbers.
    Template appears stale
    Run view:clear and check the view name/path. A .breeze.php view takes precedence over a same-named .php view. Templates are trusted PHP, not a sandbox.
    Log file is absent
    Storage is created only on a written entry. Check LOG_LEVEL filtering, write permissions, symlink restrictions, and PHP server diagnostics. Retention runs on writes, not a timer.

    Before production

    • Serve only public/, enforce HTTPS, set APP_ENV=production and APP_DEBUG=false, and configure secure cookies correctly behind a proxy.
    • Protect .env, private storage, database/backups, mail contents, and log files. Align Linux service/CLI ownership or restrict Windows NTFS ACLs.
    • Back up schema/data and encryption keys separately. Review every migration/seeder and test restoration before using --force.
    • Guard private routes and apply per-record authorization; neither valid tokens nor random file keys grant object ownership.
    • Set upload/request/time/disk/user quotas; consider quarantine and malware scanning. MIME checks do not prove a document harmless.
    • Configure SMTP/IMAP certificate trust and schedule bounded queue workers without overlapping unsafe recovery tasks.
    • Keep public API docs disabled unless intentionally needed; do not enable credential persistence in Swagger.
    • Run the native suite and separate deployment-specific Windows/MySQL checks where applicable. A CI configuration is not evidence that a specific deployment was tested.

    Language Convention

    All framework-maintained UI, CLI output, diagnostics, emails, generated code, comments, tests, and documentation use US English. The main web layout and Swagger UI declare lang="en-US". CLI examples use page='New page' as the default page. Standard messages include Check your input., This field is required., Use at least 2 characters., and Something went wrong. Please try again later. The reset and verification email subjects are Reset your password and Verify your email address. The example greeting is Hello, Ada!.     Getting Started

    Requirements: PHP 8.3+, PDO, pdo_sqlite for SQLite or pdo_mysql for MySQL, and the standard session, json, and filter extensions. The tests also use native process and socket functions. The CLI uses proc_open for the development server and tests; this function must be available for those tasks. Encryption requires the native openssl extension with AES-256-GCM support. Excel and Word creation require the native zip extension; PDF creation requires iconv. The document tests also use the native dom extension. Localized formatting requires the native intl extension and its ICU data. Upload validation requires native fileinfo; DOCX/XLSX upload checks also require native zip. PHP file uploads must be enabled. No package installation is required.

    php breeze init
php breeze migrate
php breeze db:seed
php breeze test
php breeze serve

    Open http://127.0.0.1:8000. The example form demonstrates CSRF, validation, and safe HTML output. The development server stays on localhost. Use php breeze serve 8080 for a different port. The home/test page has a responsive light design with local CSS in public/assets/welcome.css, a test form with error and success messages, and expandable CLI examples. No external fonts or scripts are loaded.

    init creates a local .env, but never overwrites an existing one. The default is SQLite in database/app.sqlite; the database is created by the first database command. The form does not need a database.

    Windows and Linux

    Use the same commands on both systems with php breeze .... On Windows, this works from PowerShell or cmd, without WSL, Bash, or an executable shebang. Make sure PHP CLI is in PATH; check with php -v and use php --ini to find the configuration file in use. PHP for your web server may use a different configuration file.

    On Windows, enable the required extensions in php.ini: pdo_sqlite for SQLite, pdo_mysql for MySQL, and also openssl and iconv for email. Enable zip for Excel/Word creation and dom for the document tests. Enable intl for localized date/time and number formatting. Enable fileinfo for upload validation. Use the correct DLLs for your PHP distribution. OpenSSL requires a valid CA bundle; set openssl.cafile if needed or use the separate SMTP_CA_FILE/IMAP_CA_FILE settings. Do not disable certificate verification.

    Relative database paths are always relative to the project root. Both database/app.sqlite and database\app.sqlite are allowed. Full Windows drive paths and UNC paths are recognized, for example:

    DB_DATABASE="C:/Data/PBreeze/app.sqlite"

    Backslashes are also allowed and are not treated as .env escapes. Do not use drive-relative paths such as C:app.sqlite. UNC paths are recognized as absolute, but use local storage for SQLite: SMB/NFS file locking is not a substitute for a database server. Use MySQL for shared databases.

    The CLI starts PHP without a shell, so spaces, percent signs, and other shell characters in project paths are preserved. Generators reject Windows device names such as CON, NUL, and COM1 on both systems. Also keep the exact capitalization of files and require_once paths consistent: Linux is generally case-sensitive, Windows generally is not.

    Linux uses POSIX file permissions: new .env and SQLite files get 0600. Windows uses existing/inherited NTFS ACLs; chmod(0600) does not provide comparable protection there. Therefore, before initialization, use Windows folder security to restrict access to the project folder, data folder, and their backups to the administrator and PHP service user. Give the service user write access only where needed. On Windows, tests check read/write access, not Unix permission bits.

    For local development, php breeze serve works on both systems. In production, you can use Apache on either system with public/ as the document root and the included .htaccess with mod_rewrite. For IIS, configure PHP through FastCGI, set the site root to public/, and configure URL Rewrite to index.php for nonexistent files. IIS does not read .htaccess. HTTPS and blocking hidden files must also be configured at the server level there.

    For scheduled email delivery, use cron on Linux and Task Scheduler on Windows. Choose the full path to php/php.exe as the program, provide the absolute path to breeze and mail:work 50 as arguments, and set the project folder as the working directory. Put paths containing spaces in quotes.

    Application Logging

    Use the native $app->log service for structured application logs. No Composer, PSR interface, database migration, or external logging package is required.

    $app->log->info('Report created.', ['report_id' => 42]);
$app->log->warning('Delivery delayed.', ['attempt' => 2]);
$app->log->error('Processing failed.', ['exception' => $exception]);
$app->log->log('notice', 'Import completed.', ['rows' => 120]);

    Available methods/levels, from lowest to highest severity, are debug, info, notice, warning, error, critical, alert, and emergency. Configure the minimum level and retention in .env:

    LOG_LEVEL=debug
LOG_RETENTION_DAYS=5

    The corresponding application configuration keys are log_level and log_retention_days. Retention must be an integer from 1 through 3650. Levels are lowercase and validated when the application is constructed. Standalone usage is also supported:

    $logger = new \PBreeze\Logger($app->root, retentionDays: 5, minimumLevel: 'info');
$logger->notice('Maintenance completed.');

    Logs are newline-delimited JSON in storage/logs/app-YYYY-MM-DD.jsonl. Each entry contains a UTC ISO-style timestamp with microseconds, level, message, and context. Embedded line breaks are JSON-escaped; a message cannot inject a second log record. Directories are created lazily with 0700 and files/locks use 0600 on Linux. On Windows, restrict inherited NTFS ACLs to the administrator and PHP service user. Storage stays outside public/, rejects symlinked directories/files, and is ignored by the existing Git rules. Never expose the storage directory through a web-server alias.

    Concurrent writers serialize through a private file lock. After each written entry, retention removes only matching daily log files older than the retained UTC calendar window: five days means today plus the previous four dates. Unrelated files and symlinks are not removed. Cleanup runs on writes, not on a background schedule; filtered entries do not trigger cleanup. Files are daily, not size-rotated: provision disk space, choose an appropriate minimum level, and monitor write failures.

    Context supports nested arrays, scalars, null, and exceptions. Sensitive keys containing password, secret, token, authorization, cookie, credential, or API/ private-key names are recursively replaced with [REDACTED]. Exceptions are reduced to class, source file, and line; exception messages, traces, previous exceptions, and arguments are deliberately omitted because they may contain credentials or request data. Context is limited to eight nested levels and each serialized entry to 64 KiB. Unsupported objects/resources, invalid UTF-8, nonfinite numbers, recursive/deep context, or oversized entries throw explicitly. Messages are plain text; there is no placeholder interpolation.

    Redaction is not a general secret detector. It does not inspect arbitrary message text or values under unrelated keys. Do not log passwords, tokens, connection strings, full request objects, uploaded contents, or personal data. Choose safe, minimal context fields explicitly.

    Unexpected web/API errors are logged automatically through the configured application logger while existing public error responses remain unchanged. Server-side HTTP exceptions (5xx) are also logged; ordinary validation, authentication, and other 4xx responses are not. API errors caught inside the API router use the same logger. CLI command failures after application startup are logged except invalid-argument/usage errors. There is no automatic access log or request-body/header/query logging.

    Direct logger writes throw on failure. Automatic exception reporting catches logging failures and explicitly reports a safe diagnostic to PHP's server log without recursively invoking the file logger. Errors before application initialization also use the PHP server log; the CLI still prints its error and exits with a failure status. This service does not install global error/exception handlers or capture engine fatal errors/shutdown events: keep PHP's log_errors and server monitoring configured. A minimum level above error also filters automatic application-error entries.

    File Uploads

    Web routes accept native PHP multipart/form-data uploads through Request. Use an explicit list of allowed filename extensions for each upload handler. There is deliberately no allow-all default. The default per-file size limit is 2 MiB (2,097,152 bytes).

    Configure the application default in .env:

    UPLOAD_MAX_BYTES=2097152

    This must be a positive integer number of bytes. It configures $app->uploads->maxBytes through upload_max_bytes in the application config. It does not change PHP's upload_max_filesize or post_max_size.

    Supported types are jpg, jpeg, png, gif, webp, pdf, txt, csv, docx, and xlsx. Use lowercase extensions without a dot. Uploaded extension matching is case-insensitive. PHP/script files, HTML, SVG, arbitrary ZIP archives, and legacy .doc/.xls files are not supported.

    Receiving and Storing a File

    Register a protected web route in routes/web.php:

    use PBreeze\HttpException;
use PBreeze\Request;
use PBreeze\Response;

$router->post('/documents', $app->auth->protect(
    static function (Request $request) use ($app): Response {
        $file = $request->file('document');
        if ($file === null) {
            throw new HttpException(422, 'Choose a document to upload.');
        }
        $stored = $app->uploads->store(
            $file,
            allowedTypes: ['pdf', 'docx', 'xlsx'],
        );

        // Persist these values with the current user's ID in your own model.
        // Delete the stored upload if your database write subsequently fails.
        return Response::json([
            'key' => $stored->key,
            'name' => $stored->originalName,
            'mime' => $stored->mimeType,
            'size' => $stored->size,
        ], 201);
    },
));

    In a Breeze template, submit a multipart form with the normal CSRF field. Pass 'session' => $app->session in the view's render data:

    <form action="/documents" method="post" enctype="multipart/form-data">
    @csrf($session)
    <label for="document">Document</label>
    <input id="document" name="document" type="file" accept=".pdf,.docx,.xlsx" required>
    <button type="submit">Upload document</button>
</form>

    The browser's accept attribute is only a selection hint, not validation. JavaScript clients may send the CSRF token in X-CSRF-Token; let the browser set the multipart boundary when using FormData.

    file() returns an UploadedFile or null for a missing field/no file selection. If more than one file is supplied to a single-file accessor, it throws HTTP 400. files() always returns a list; missing selections are omitted. One-dimensional documents[] and keyed file lists are supported; deeper nested upload fields are rejected with HTTP 400. Nonempty PHP upload failures remain accessible and are reported by validation.

    The uploaded object exposes originalName, clientMediaType, and PHP's error code. Client path components are removed from the original name; the remaining UTF-8 name must contain 1 to 255 bytes without control characters. Treat this name as display metadata and escape it in HTML. The client media type is explicitly untrusted and is never used to approve or serve a file.

    store() validates before writing. It returns a StoredUpload with read-only key, originalName, mimeType, and actual byte size properties. It uses is_uploaded_file() and move_uploaded_file(): arbitrary local server files and CLI-created temporary files cannot be passed off as uploads. Each file receives a cryptographically random 64-hex-character key plus its validated extension. Files are stored as storage/uploads/<random-id>/file.<extension>, never under the client's name, so equal original names cannot overwrite one another.

    Storage directories are created on demand with 0700 permissions and files receive 0600 on Linux. On Windows, restrict inherited NTFS ACLs to the administrator and PHP service user. The storage location is outside public/; symlinked storage directories and symlinked stored files are rejected. Upload contents are ignored by the existing storage/ Git ignore rule.

    There is no automatic attachment database table or ownership model. Persist the storage key, display name, size, media type, and owner as your application requires. Keys locate files; they are not authorization credentials. No public upload/download routes are installed by this feature.

    Multiple Files and Custom Limits

    $files = $request->files('documents');
if ($files === [] || count($files) > 5) {
    throw new \PBreeze\HttpException(422, 'Choose between one and five files.');
}

// Check every file before starting a batch write.
foreach ($files as $file) {
    $metadata = $app->uploads->validate($file, ['jpg', 'jpeg', 'png'], maxBytes: 524288);
}
foreach ($files as $file) {
    $stored = $app->uploads->store($file, ['jpg', 'jpeg', 'png'], maxBytes: 524288);
    // Persist each file and its owner.
}

    Use an input with name="documents[]" and the multiple attribute. $app->uploads->validate($file, $allowedTypes) performs the same checks as store() without moving the file, using the configured default, returning extension, canonical mime, and actual byte size. The optional positive integer maxBytes overrides the configured per-file default; it does not raise PHP or web-server limits. Empty files are rejected. Calling $file->validate() directly is standalone validation and retains a 2 MiB default unless you explicitly pass maxBytes; use the application service for environment-aware validation.

    Batches are not filesystem/database transactions. Prevalidating a batch avoids starting writes for an already-invalid file, but disk or database failures can still occur later. Track successful keys and clean them up if the operation must be all-or-nothing. Enforce application-specific file-count, combined-byte, user-quota, and rate limits.

    Protected Downloads and Deletion

    After authenticating a user and loading an attachment record belonging to that user, return:

    return $app->uploads->download($attachment['storage_key'], $attachment['original_name']);

    Register the download action with $app->auth->protect(...) and perform the ownership/record authorization check before calling download(). Never authorize access just because someone knows a random storage key. download() itself is a storage operation, not an authorization service. Its optional filename defaults to download.<extension>; the original name must come from your persisted metadata if you want to restore it.

    Downloads reuse the normal attachment response: canonical media type, UTF-8-safe filename headers, correct byte length, nosniff, and no-store. HEAD requests omit the response body. Invalid keys, missing files, and symlinked file targets produce HTTP 404. Files are read into memory to build the response; bound upload limits accordingly.

    After the same authentication and ownership checks, a CSRF-protected POST or DELETE handler may call:

    $app->uploads->delete($attachment['storage_key']);

    This removes only that stored file and its random directory. Coordinate deletion of your database metadata explicitly; deleting an attachment record does not automatically delete the file, and deleting a file does not update your database.

    Validation and Deployment Limits

    • Validation checks the real temporary file size, allowed extension, and server-detected media type using native fileinfo, not client-provided size/type claims.
    • Images also undergo a native header/dimension check. This is not a full image decode, re-encoding service, or pixel-count limit; add application image-dimension limits before further processing untrusted images.
    • DOCX/XLSX files must be ZIP packages containing the matching main document, content-type, and relationship entries. Checks reject macro-named entries, encrypted entries, unsafe archive paths, more than 1,000 entries, entries larger than 10 MiB, or a combined declared expansion larger than 20 MiB. Archives are not extracted. These are bounded package-shape checks, not complete Office schema validation or a guarantee of harmless content.
    • MIME/header checks are not malware scanning or content sanitization. PDFs and Office documents may contain active content or external links. Uploaded CSV files may contain spreadsheet formulas; validation does not rewrite their contents. Add quarantine/scanning if your deployment requires it. Do not execute, include, extract, or render uploaded content inline simply because it passed validation.
    • file_uploads must be enabled. Configure a writable PHP upload_tmp_dir and writable private storage. Enable native fileinfo; Office checks additionally need zip.
    • PHP's upload_max_filesize must accommodate the per-file limit; post_max_size must accommodate all files, form fields, and multipart overhead. For a single 2 MiB file, a typical starting point is upload_max_filesize=2M and post_max_size=8M. Configure these in the PHP configuration used by your actual web server.
    • PHP's max_file_uploads, max_input_vars, and max_input_nesting_level can limit parsed fields. PHP may omit files/fields beyond its parsing limits; handlers must check required fields and expected file counts.
    • Web-server/reverse-proxy body-size limits also apply. Raising framework maxBytes cannot bypass them.

    The request layer returns HTTP 413 when a POST exceeds PHP's configured post_max_size, rather than treating PHP's discarded body as an empty form. Per-file PHP size failures and framework size failures also return 413; partial files, disallowed types, invalid images/packages, empty files, and untrusted local-file sources return 422. Malformed file-field structures return

    1. Server receive/storage failures throw and use the standard logged,

    generic HTTP 500 response. Application-required file errors should be explicitly reported by the handler, as in the example above.

    Multipart support is for normal POST web routes, preserving session/CSRF behavior. The separate /api/* router remains JSON-only and rejects multipart bodies with HTTP 415 (or 413 when its request-size limit is exceeded). Native PHP does not populate this API for raw PUT/PATCH uploads, chunked upload protocols, remote URLs, or base64 JSON file payloads.

    Date, Time, Money, and Decimal Formatting

    The shared $app->format service uses native PHP Intl/ICU without Composer or external packages. Defaults are en-US and UTC; configure them in your local .env:

    APP_LOCALE=en-US
APP_TIMEZONE=UTC

    The application configuration uses locale and timezone keys. You can also create a standalone formatter:

    $format = new \PBreeze\Formatter(locale: 'de-DE', timezone: 'Europe/Berlin');

    Use language tags such as en-US, nl-NL, de-DE, fr-FR, hi-IN, or ar-EG. Optional script and region subtags are supported; ICU extensions and locale keywords are not. ICU may fall back to a supported parent locale; an unsupported language throws instead of silently using the machine's default. Use IANA time zone identifiers such as UTC, America/New_York, or Europe/Amsterdam, not ambiguous abbreviations or numeric UTC offsets. Neither formatter creation nor individual calls change PHP's global time zone or Intl's global locale. Missing Intl is reported when formatting is requested, so unrelated framework features do not require it.

    Dates and Times

    $date = new \DateTimeImmutable('2026-11-13T15:45:06+00:00');

$app->format->date($date, 'short'); // 11/13/26
$app->format->date($date);          // Nov 13, 2026
$app->format->date($date, 'long');   // November 13, 2026
$app->format->date($date, 'full');   // Friday, November 13, 2026
$app->format->time($date, 'short');
$app->format->dateTime($date);

$app->format->date($date, 'short', locale: 'de-DE'); // 13.11.26
$app->format->dateTime(
    $date,
    locale: 'en-US',
    timezone: 'America/New_York',
    pattern: 'yyyy-MM-dd HH:mm:ss XXX',
); // 2026-11-13 10:45:06 -05:00

$app->format->dateTime(0, pattern: 'yyyy-MM-dd HH:mm:ss'); // 1970-01-01 00:00:00

    Inputs are DateTimeInterface objects or integer Unix timestamps in seconds. Strings are intentionally not parsed; construct and validate your dates explicitly. Dates are formatted in the configured or overridden time zone, not necessarily the input object's zone, without mutating that object. IANA daylight-saving rules apply.

    date() and time() default to medium. dateTime() defaults to a medium date and short time. Styles are short, medium, long, and full; for dateTime(), either part may be none. At least one part must be visible unless a custom pattern is supplied.

    The optional pattern uses **ICU syntax, not PHP date() syntax**. For example, yyyy-MM-dd is a numeric date and HH:mm:ss is 24-hour time. Quote literal text using ICU apostrophe rules. A pattern overrides the style layout and must contain 1 to 256 UTF-8 bytes without control characters. Localized punctuation, spacing, and names can vary with the installed ICU version. The calendar is explicitly Gregorian.

    Decimal Numbers and Percentages

    $app->format->decimal('1234.5');                       // 1,234.50
$app->format->decimal('1234.5', precision: 3);         // 1,234.500
$app->format->decimal(1234, precision: 0);             // 1,234
$app->format->decimal('1234.5', locale: 'de-DE');       // 1.234,50
$app->format->decimal('12345678.5', locale: 'hi-IN');   // 1,23,45,678.50
$app->format->decimal('1234.5', grouping: false);      // 1234.50
$app->format->decimal('1.005');                        // 1.01
$app->format->decimal('-1.005');                       // -1.01

$app->format->percent('0.125');                       // 12.50%
$app->format->percent('0.125', precision: 1);          // 12.5%
$app->format->percent('0.125', locale: 'de-DE');        // 12,50 %

    Decimal and percent inputs are integers or decimal strings. The precision range is 0 through 20, defaulting to exactly 2 fractional digits. Rounding is half away from zero, performed on strings without binary floating-point conversion. Negative values that round to zero display as positive zero. Percent inputs are ratios: 1 means 100%, not 1%.

    Grouping sizes, decimal/group separators, digits, signs, and percent placement follow ICU locale rules. Some locales use nonbreaking spaces or non-Latin digits, and some do not group four-digit numbers. Do not compare rendered values after replacing those characters with ordinary spaces.

    Money

    $app->format->money('1234.565', 'USD');                 // $1,234.57
$app->format->money('1.005', 'USD');                    // $1.01
$app->format->money('1234.5', 'EUR', locale: 'de-DE');   // 1.234,50 €
$app->format->money('1234.5', 'JPY');                   // ¥1,235
$app->format->money('1.2345', 'KWD');                   // KWD 1.235
$app->format->money('1234.5', grouping: false);         // $1234.50

$app->format->moneyMinor(12345, 'USD');                 // $123.45
$app->format->moneyMinor(-1, 'USD');                    // -$0.01
$app->format->moneyMinor(12345, 'JPY');                 // ¥12,345
$app->format->moneyMinor(12345, 'KWD');                 // KWD 12.345

    money() accepts a decimal string in major currency units; moneyMinor() accepts an integer in the currency's minor units. Floats are not supported inputs: keep database decimal amounts as strings, and do not compute money with floating-point arithmetic before calling the formatter. The default currency is USD. Pass uppercase three-letter ISO 4217 codes; syntax is checked, but this is not a registry of currently active currencies. Unknown codes use ICU's generic currency formatting.

    ICU supplies standard currency precision: typically 2 digits for USD/EUR, 0 for JPY, 3 for KWD, and 4 for CLF. This is not a universal cents conversion. String rounding remains exact even beyond PHP's integer range or Excel's numeric precision; integer minor units are limited to PHP's integer range. Currency position, symbol/code, spacing, negative sign, and digits follow the requested locale. Space characters in the examples above may actually be nonbreaking spaces. No currency conversion, accounting arithmetic, cash rounding increments, or localized-input parsing is performed.

    For all numeric methods, decimal strings use ASCII digits, an optional leading minus, and an optional period followed by fractional digits. No whitespace, leading plus, grouping separators, or exponent notation is accepted. Inputs are limited to 1,024 bytes. Decimal and percentage inputs also reject floats: use strings when fractional precision matters. For example, "0.1" is valid; "1,25", ".5", and "1e3" are not.

Stream-wrapper URLs, drive-relative Windows paths, control characters, and nonportable basenames are rejected. Files receive 0600 permissions on Linux; restrict inherited ACLs on Windows. Incomplete writes are removed, and failures throw exceptions.

    download() returns a normal PBreeze\Response with an attachment disposition, the correct media type and byte length, nosniff, and no-store. UTF-8 filenames use filename* with an ASCII fallback; filenames cannot contain paths or control characters. Give the filename the matching extension. Return the response rather than printing file bytes yourself, so normal HEAD handling and response headers remain intact.

}));

    CSV uses UTF-8 without a BOM, CRLF record endings, doubled double quotes, and no proprietary backslash escape. Delimiters may be comma, semicolon, tab, or pipe.     CSV spreadsheet-formula protection is enabled by default. This intentionally changes those text values; numeric cells remain numeric text. Use protectFormulas: false only for trusted data when an exact raw export is necessary. Importer behavior varies: retain protection when opening untrusted CSV in spreadsheet software.

    XML string keys become element names and integer keys become <item>: the people list above becomes <people><item><name>Ada</name>...</item>...</people>. Null produces an empty element. Attributes, namespace declarations, raw markup, DTDs, and entities are not accepted as data features. Text is escaped, not interpreted.

    JSON preserves native JSON value types and throws on invalid UTF-8, recursive data, unsupported values, or nonfinite numbers. CSV, XML, and office-document text must be valid UTF-8 containing only XML 1.0 characters; unsupported cell types and nonfinite numbers throw instead of being silently converted.

Leading zeros are retained in string identifiers. Excel numeric precision is approximately 15 significant digits: pass long identifiers as strings. Dates should be formatted as strings. This baseline does not provide formulas, charts, styling, date-number formats, macros, or reading existing workbooks.

    Creating, Viewing, and Revoking Tokens

    First register at /register and verify the email address through the existing verification email. Tokens are intentionally issued only through the admin CLI: there is no public password/token endpoint, OAuth server, or additional login without CAPTCHA. Use the numeric ID from the users table, not the email address:

    php breeze api:token 1 laptop 30
php breeze api:tokens 1
php breeze api:revoke 12

    api:token <user-ID> [name] [days] displays the new pbz_... token once. The default expiration is 30 days; the allowed range is 1–365 days. api:tokens displays only the ID, user ID, name, and timestamps, including for expired tokens; api:revoke uses the token ID, not the user ID. Store the token in a secret store, not in source code, query strings, shell history, or shared terminal logs. The database stores only the SHA-256 hash.

    For an API client, send the token in the Authorization header using bearer authentication. Cookies, query parameters, and CSRF tokens never authenticate API requests. A token is valid only while the user exists, the email address is verified, the expiration date has not passed, and the stored session_version matches. Password reset therefore also invalidates all existing API tokens. Web logout removes only the web session; revoke API tokens separately. Tokens have no scopes/roles: they represent the user. Always implement your own per-object authorization; a valid token does not automatically grant access to other users' data.

    Creating an API with the CLI

    php breeze make:api Products

    This creates:

    • app/controllers/api/ProductsApiController.php;
    • routes/api/products.php with GET/POST /api/products and GET/PUT/DELETE /api/products/{id};

    $api->add('POST', '/api/echo', static function (\PBreeze\Request $request): \PBreeze\Response {
    $data = \PBreeze\Api::validate($request, [
        'message' => 'required|string|min:2|max:200',

}, [

    'operationId' => 'echoMessage',
    'requestBody' => ['required' => true, 'content' => [
        'application/json' => ['schema' => [
            'type' => 'object',

    ]],

]);

    Pass false as the fifth argument only for intentionally public endpoints. summary, a unique operationId, and responses are required.     JSON, Errors, and Limits

    Nonempty API bodies require Content-Type: application/json and a JSON object. Invalid JSON returns 400, other body types 415, and bodies larger than 1 MiB 413. Empty bodies without a JSON content type are allowed, for example with DELETE. Also configure limits in PHP, the web server, and the proxy: PHP may process uploads before application code runs. Normally parsed API requests have a fixed database rate limit of 120 requests per direct client IP per calendar minute; after that, HTTP 429 with Retry-After. Documentation and OpenAPI are exempt and do not require a database. REMOTE_ADDR is used, not unverified proxy headers. Clients behind a proxy therefore share the proxy IP; apply additional limits at the edge. This limit is not DDoS protection.

    API errors consistently use:

    {"error":{"status":422,"message":"Check your input.","details":{"message":["This field is required."]}}}

    details is present only for validation errors. Unknown routes return JSON 404, incorrect methods return JSON 405 with Allow, and missing/invalid tokens return JSON 401 with WWW-Authenticate. Unexpected errors are logged and return a generic JSON 500, even in debug mode. Use Response::json() for custom API responses; for an empty 204, use an empty Response with a JSON content type. API requests do not start a session or set a session cookie. The existing web CSRF check remains unchanged. There is intentionally no automatic CORS or preflight configuration; clients on a different origin require an explicit, carefully restricted policy.

    Compilation and Cache

    Sessions and CSRF

    All POST, PUT, PATCH, and DELETE requests require a session token. Only GET, HEAD, and OPTIONS are exempt; do not modify data with them.

    <form action="/berichten" method="post">
    <?= csrf_field($session) ?>
    <button type="submit">Save</button>
</form>

    Pass $this->app->session to the view as session. A JSON client can send the same token as X-CSRF-Token, along with the session cookie. An incorrect or missing token returns 419. There are intentionally no default CSRF exceptions or unprotected API routes. For a form with bot protection, also send the CAPTCHA fields and empty honeypot; a CSRF token alone is not sufficient.

    $this->app->session->put('notice', 'Saved');
$notice = $this->app->session->get('notice');
$this->app->session->regenerate();

    Authentication automatically regenerates the session ID and CSRF token on login and logout. Existing session data is cleared at that time. A CSRF token does not replace access control; explicitly protect your routes.

    CAPTCHA and Honeypot

    The selected forms use both controls: registration, login, forgot password, verification-email resend, and the name form on the home page. Logout, confirming a verification link, and saving a new password remain protected by CSRF and their own guards/tokens and existing limits, without an additional CAPTCHA.

    The CAPTCHA is entirely native PHP: no external services, JavaScript, GD, fonts, Composer, or API key. GET /captcha/{id} returns a local SVG with six random characters, drawn as vector paths with light noise. The solution is not present as text or metadata in the HTML/SVG; the session stores its SHA-256 hash, along with the SVG, form name, and expiration time. Ambiguous characters 0, 1, I, and O are not used.

    User Experience

    • Enter the six characters; capitalization does not matter. Leading and trailing spaces are ignored.
    • A code is valid for five minutes and works only in the same session and for the same form purpose.
    • Each submission attempt consumes the supplied code, even with an incorrect answer, a filled honeypot, or another validation error. The form then displays a new code; password fields remain empty.
    • Show another code refreshes through a CSRF-protected POST without performing the form action, logging in, or sending email. The browser does not need to validate other fields first. Name/email values are preserved; passwords are not. The form's old code is revoked.
    • Fetching images or making HEAD requests does not consume a code. Images are session-bound and are not cached.
    • Up to twelve unexpired codes per session support multiple tabs. If there are more, the oldest code expires. Up to sixty new codes per session per minute; after that, 429 with Retry-After is returned.
    • The website honeypot must be present as an empty string. The field is visually hidden, removed from the tab order, and hidden from screen readers; autocomplete is disabled. Filled, missing, or incorrectly typed values are rejected.

    Bot-check errors return 422 with a generic message and a new form. Missing/incorrect CSRF remains 419 and is checked earlier. No success message is displayed for a blocked action. The existing database-backed authentication limits remain active when the bot check passes.

    Limitations: a simple SVG CAPTCHA can be solved by OCR, pattern recognition, or human-solving services. The honeypot is an additional hurdle, not proof that a visitor is human. The creation limit is session-bound; new cookies bypass that limit. Also use request limits per IP and abuse detection on your trusted web server/proxy. A visual CAPTCHA is not independently usable by blind users: there is no audio or equivalent accessible verification route yet. Provide one before offering these forms to an audience for whom visual verification is inaccessible; do not add an unprotected bypass.

    Sending Email

    Authentication emails always go through the existing database queue, even if MAIL_LOG=false. Configure MAIL_FROM and SMTP as described below, and run this regularly through cron or Windows Task Scheduler:

    php breeze mail:work 50

    Successful submission means the email is queued, not that it has been delivered. Without working SMTP configuration/worker, the user receives no email. No external email is sent during installation or tests. New accounts and their verification email are stored together: if queuing fails, registration is rolled back. Database and configuration errors are logged as server errors, not displayed as successful submissions.

    Tokens contain 32 cryptographically random bytes and are stored only as SHA-256 hashes in auth_tokens. Verification tokens are valid for 24 hours, reset tokens for 30 minutes, measured from the request. They are single-use; a new request replaces the previous link for the same purpose. The worker must therefore run promptly. Reset invalidates all existing login sessions for the account and signs out the requester. Reset does not automatically verify the email address.

    Warning: the sendable email in emails necessarily contains the full link. Protect the database, backups, and CLI access as secrets. Delete old emails according to your retention policy and configure web server/proxy logs not to retain token-bearing query strings. Authentication pages use no-store and Referrer-Policy: no-referrer.     Native ORM and Query Builder

    The ORM consists of framework/Query.php and framework/Model.php, explicitly loaded in the bootstrap. Each query and model receives the existing Database instance.     Table Queries: Arrays

    $query = $app->db->table('notes');
$id = $query->insert(['title' => 'My note']);
$note = $query->find($id);          // array of null
$note = $query->findOrFail($id);    // array of RecordNotFoundException

$recent = $query->where('id', '>', 0)
    ->where('title', 'LIKE', '%note%')
    ->orderBy('id', 'desc')
    ->limit(20)
    ->get();

$query->where('id', $id)->update(['title' => 'Updated']); // row count
$query->where('id', $id)->delete();                       // row count

    Queries are immutable: where, orderBy, limit, and offset return a new query. Therefore, retain the result or chain the calls. All where conditions are combined with AND:

    $query = $app->db->table('notes');
$filtered = $query->whereIn('id', [1, 2, 3])->whereNotNull('title');
$first = $filtered->first();            // array or null
$first = $filtered->firstOrFail();      // exception if absent
$count = $filtered->count();            // int
$exists = $filtered->exists();          // bool
$rows = $filtered->orderBy('id')->limit(10)->offset(10)->get();

    Supported operators: =, !=, <>, <, <=, >, >=, LIKE, NOT LIKE. where('column', $value) uses =. where('column', null) and where('column', '!=', null) use IS NULL and IS NOT NULL, respectively; explicit whereNull/whereNotNull are also available. whereIn expects a list of up to 500 non-null values; an empty list finds or modifies no rows. LIKE wildcards % and _ retain their SQL meaning: parameter binding does not make them literal.

    Values are bound as int, bool, string, or null; floats are bound as textual numbers. Arrays, objects, resources, INF, and NAN are rejected. Table and column names must be simple identifiers (letters, digits, or underscores, not starting with a digit); they are quoted. Operators and sort directions are checked. The builder does not accept SQL fragments, joins, aliases, schema/table prefixes, OR groups, or raw expressions. For more complex SQL, intentionally use Database::execute() with bindings. Even with valid column names, choose yourself which ones a user may query or modify: identifier validation is not authorization.

    update and delete without an explicit WHERE are rejected. Writes with sorting, limits, or offsets are also rejected so conditions are never silently ignored. insert/create does not accept filters, sorting, or pagination. insert([]) uses database defaults and returns the PDO insert ID (int if representable, otherwise string); with manual keys, use the supplied key, not this driver-dependent ID. get() retrieves all matching rows unless you specify a limit. count() and exists() use the filters and ignore read limits, offsets, and sorting. offset with get() requires an explicit limit.

    Models: Objects

    php breeze make:model Article

    The generator creates a Model subclass with a snake_case name plus s as the default table name. There is intentionally no language-dependent pluralization: check the name, create the table through a migration, and populate $fillable. The default list is empty: no fields are mass assignable.

    <?php
declare(strict_types=1);

namespace App\Models;

final class Article extends \PBreeze\Model
{
    protected string $table = 'articles';

}

    Encryption

    The native Encryption service uses AES-256-GCM through OpenSSL: 256-bit keys, a new cryptographically random 12-byte nonce per encryption, and a full 16-byte authentication tag. Data is returned only if the integrity check succeeds. There is no fallback to plaintext, a default key, or insecure encryption.

    Creating and Storing a Key

    php breeze key:generate

    This displays one APP_KEY=base64:... line. Copy it to your local .env or set APP_KEY through your deployment's environment configuration/secret store. The command changes no files and never overwrites an existing key. Each execution displays a new key; do not casually replace a key that already protects data. --force is not accepted. Run the command in a private terminal, not in shared CI logs.

    The key must contain exactly 32 random bytes, canonically base64-encoded with the base64: prefix; a password or custom text key is rejected. No key is automatically generated at boot or per request. Without APP_KEY, the framework continues to work until you use encryption or a non-null encrypted cast; then an explicit EncryptionException is thrown.

    Store a secure key backup separately from the database. Share the same key with the web app, CLI, and workers that must decrypt the same data; use different keys for different applications/environments. Never commit real keys. Protect .env, environment variables, server logs, and backups; do not dump the application configuration. Encrypted data cannot be recovered without the original key.

    Using the Service

    $encrypted = $app->encryption->encrypt('Confidential text', 'orders:notes');
$plaintext = $app->encryption->decrypt($encrypted, 'orders:notes');

    The optional context is authenticated but not stored in the payload. You must use exactly the same context to decrypt. Choose a fixed, application-specific context to prevent accidental reuse elsewhere. Empty strings, Unicode, and binary strings are supported. The output format is pbreeze:v1: followed by base64 of the nonce, tag, and ciphertext. The prefix/version and context are included as additional authenticated data. Encrypt the same value again and you get a different payload. The format does not use PHP serialization.

    use PBreeze\Encryption;

$encryption = new Encryption($configuredKey);
$encrypted = $encryption->encrypt($value);
$value = $encryption->decrypt($encrypted);

    Invalid/outdated payload formats, truncated or modified data, or an incorrect key or context throw PBreeze\EncryptionException. A genuine operational failure must remain visible; do not catch it and then return empty text or the original ciphertext as if decryption succeeded. Errors contain no key or plaintext. Key and plaintext parameters are marked with SensitiveParameter; the service redacts key data in var_dump and cannot be serialized. This does not replace careful logging practices: your own code can still leak decrypted data.

    Encrypted ORM Casts

    final class Customer extends \PBreeze\Model
{
    protected string $table = 'customers';
    protected array $fillable = ['name', 'private_note', 'preferences'];
    protected array $hidden = ['private_note', 'preferences'];
    protected array $casts = [
        'private_note' => 'encrypted',
        'preferences' => 'encrypted:json',
    ];
}

$customers = new Customer($app->db);
$customer = $customers->create([
    'name' => 'Example',
    'private_note' => 'For internal use only',
    'preferences' => ['language' => 'en'],
]);
$text = $customer->private_note;       // decrypted string
$preferences = $customer->preferences; // decrypted array
$customer->update(['private_note' => 'New text']);

    encrypted accepts strings; encrypted:json accepts arrays. Both preserve null as database NULL. Bulk updates through a model query also use these casts. Hydration/refresh validates ciphertext without re-encrypting: unchanged data is not marked dirty and does not change during another field update. Assigning the same decrypted value again preserves the existing ciphertext. Deliberately assign new content if you want to replace it.

    Use TEXT or, for large payloads, MySQL LONGTEXT, not the original short VARCHAR: encryption adds 28 bytes and a prefix, and base64 further increases the payload. The exact storage length is 11 + 4 * ceil((28 + bytes) / 3). No existing columns or data are modified automatically.

    The ORM context contains the table name, column name, and cast type. Moving ciphertext to another table/column or changing the cast type is therefore rejected. The context does not contain a row ID: moving data between rows in the same column or restoring older valid data is not prevented. Encryption does not protect against replay, deletion, a compromised application, or an attacker with access to both data and key.

    Encryption does not automatically hide fields. Reading and toArray()/JSON return plaintext unless you add the field to $hidden. dirty() and direct $app->db->table(...) queries use the storage format. Table queries and handwritten SQL do not apply encrypted casts: use models when writing to encrypted columns.

    Because ciphertext is random, comparisons, whereIn with values, LIKE, sorting, and relationship keys on encrypted model fields are unusable; the model query explicitly rejects them. whereNull/whereNotNull and an empty whereIn remain usable. Primary keys and automatic timestamp columns must not have an encrypted cast. Also do not use a foreign/unique index as a logical plaintext comparison. Existing login email addresses, password hashes, reset/verification token hashes, and mail queue remain intentionally unchanged. Passwords remain one-way hashed, not reversibly encrypted.

    For a custom database instance, explicitly pass the same service:

    $db = new \PBreeze\Database($root, $databaseConfig, $encryption);

    Existing Data and Key Rotation

    Adding an encrypted cast to an existing plaintext column does not migrate anything: reading then intentionally fails. Create your own controlled migration to sufficiently large columns and encrypt existing values with the correct context. Back up first and test on a copy. Renaming a table/column also requires decrypting with the old context and encrypting with the new context.

    There is no automatic key rotation, keyring, or migration command. For a controlled rotation, stop all writers/workers, safely store the old key, decrypt with the old service, and encrypt with the new service using the same context. Verify all records/backups, switch all processes to the new key, and only then resume writes. Replacing APP_KEY alone makes previously encrypted data unreadable.

    Email: SMTP, IMAP, and Database Queue

    This uses native PHP streams, OpenSSL for TLS, and iconv for incoming MIME headers and character sets. The IMAP extension, Composer, and mail() are not required. First configure your mail server and run the new migration:

    php breeze migrate

    In production, as usual, use php breeze migrate --force. An existing .env is not automatically updated. Add the following settings yourself; the full list is in .env.example.

    MAIL_LOG=true
MAIL_FROM=sender@yourdomain.com
SMTP_HOST=smtp.yourprovider.com
SMTP_PORT=587
SMTP_ENCRYPTION=starttls
SMTP_USERNAME=sender@yourdomain.com
SMTP_PASSWORD="your app password"
IMAP_HOST=imap.yourprovider.com

    Use your provider's actual values; the hosts above are examples. SMTP and IMAP can use different accounts. Native password login is supported: SMTP AUTH PLAIN/LOGIN and IMAP LOGIN. Use an app password if needed. OAuth2 and providers that allow only OAuth2 are not supported.

    tls is direct TLS (commonly SMTP 465 and IMAP 993); starttls performs a required TLS upgrade (commonly SMTP 587 and IMAP 143). There is no fallback to unencrypted traffic. TLS 1.2+ with certificate and hostname verification is required for external servers. IMAP then requires PREAUTH. SMTP_TIMEOUT and IMAP_TIMEOUT are socket timeouts of 1–300 seconds, 15 by default. Hosts are DNS names or IPv4 addresses, not URLs.

    Sending or Queuing from PHP

    Through $app in routes, or $this->app in controllers:

    $message = $app->mail->compose([
    'to' => ['recipient@example.com'],
    'subject' => 'Welcome',
    'text' => 'Welcome to our application.',
    'html' => '<p>Welcome to our application.</p>',
]);

$id = $app->mail->send($message);   // Send immediately through SMTP.
// OR:
$id = $app->mail->queue($message);  // Store only; send later through the CLI.

    from is optional in compose() and defaults to MAIL_FROM. You can also directly use new \PBreeze\Mail\Message(...). Use bare ASCII email addresses without display names; up to 100 recipients. Subjects and bodies are UTF-8. You can provide text, HTML, or both; providing both creates a multipart/alternative message. Subjects must not contain control characters and are limited to 500 bytes; bodies are limited to 5 MiB total. Headers are encoded and MIME bodies are base64-encoded. Cc, Bcc, attachments, and supplied headers are not included.

    MAIL_LOG=true is the default:

    • Directly sent outgoing messages are stored in emails before SMTP. The table stores the sender, recipients, subject, text, HTML, Message-ID, status, attempts, timestamps, and a sanitized error message.
    • A database error before sending prevents the message from being sent

    without a log. An SMTP error throws an exception and remains in the table.

    • Retrieved incoming messages are stored in the same table.
    • With logging enabled, send() returns the ID; otherwise, it returns null.

    With MAIL_LOG=false, direct sending and IMAP retrieval do not use an email table. **Explicitly using queue() or mail:queue always stores a message**: a database queue cannot operate without storage. All stored outgoing messages can still be sent through the CLI, and their status is updated. Settings and passwords are not stored in the email table.

    Sending Through the CLI

    Create a JSON file yourself, for example message.json:

    {
  "to": ["recipient@example.com"],
  "subject": "Welcome",
  "text": "Welcome to our application.",
  "html": "<p>Welcome to our application.</p>"
}
    php breeze mail:queue /path/to/message.json
php breeze mail:list
php breeze mail:show 1
php breeze mail:send 1
php breeze mail:work 50

    mail:queue displays the new ID; replace 1 with that ID. The JSON file may be up to 6 MiB; the body content limit remains 5 MiB. Store such files outside public/ and do not commit confidential messages. mail:work processes one batch, oldest first, and stops at the first error with exit code 1. It is not a background daemon. You can run this command periodically through cron (Linux) or Task Scheduler (Windows), using absolute paths to PHP and breeze. mail:list, mail:show, and mail:fetch output JSON, so even untrusted subjects cannot execute terminal control codes.

    Delivery statuses:

    StatusMeaning
    queuedReady to send; the worker selects only this status.
    sendingAtomically claimed by a sending process.
    sentSMTP returned a 250 confirmation after DATA; delivery is not guaranteed.
    failedNot sent or explicitly rejected by SMTP.
    uncertainConnection lost after DATA began; SMTP may already have accepted the email.
    receivedRetrieved through IMAP; never directly sendable.
    php breeze mail:retry 1
php breeze mail:send 1

    mail:retry changes only failed back to queued. sent and incoming emails cannot be resent with these commands. Create a new message for an intentional resend. If a process crashes, the status may remain sending. In that case, first check the SMTP server and stop active workers; only then deliberately use mail:retry ID --force for sending or uncertain. This can cause duplicate delivery. There is intentionally no automatic timeout retry. The Message-ID remains the same on retries, but that does not guarantee recipient-side deduplication.

    If SMTP accepts the email but saving sent fails, the status remains sending and the caller receives an error. In that case, also check the SMTP server first. Concurrent workers can never claim the same queued row; if a claim conflict occurs, the worker stops explicitly and the next scheduled run can proceed. SMTP acceptance is not the same as delivery: bounces are not processed automatically. Configure SPF, DKIM, and DMARC at the domain/mail server level.

    Reading and Logging the IMAP Inbox

    php breeze mail:fetch 50

    Or from PHP:

    $messages = $app->mail->fetch(50);
foreach ($messages as $message) {
    $id = $message['id'];            // null when MAIL_LOG=false
    $subject = $message['message']['subject'];
    $text = $message['message']['text'];
}

    The client opens the mailbox with EXAMINE and reads BODY.PEEK[]: messages are not marked as read, deleted, or moved. The default is INBOX; other mailbox names are ASCII or pre-encoded IMAP modified UTF-7. When logging is enabled, the oldest UIDs not yet stored are retrieved so repeated batches work through the inbox. Without logging, the most recent UIDs are retrieved and there is no persistent import checkpoint. Limits are 1–1000 messages per run, 50 by default.

    Deduplication uses server, port, account, mailbox, UIDVALIDITY, and UID; the unique database index also protects concurrent imports. A changed UIDVALIDITY or account/server configuration can intentionally cause a new import. Deleted database rows can be imported again. The server is queried with UID SEARCH ALL on each run; metadata is limited to 2 MiB per response.

    Incoming MIME is parsed into text and HTML, including base64, quoted-printable, RFC 2047 headers, and iconv character sets. Attachments are not unpacked; the exact original email remains base64-encoded in raw_message. headers_json stores the original unfolded headers; outgoing emails store structured fields instead of a raw copy. Incoming to_addresses contains the original To header as a single list item, not a validated recipient list. Incoming data is never reused as an outgoing Message.

    The default maximum is 10 MiB raw per message (IMAP_MAX_BYTES), configurable up to 50 MiB; each batch is limited to 50 MiB raw. MIME nesting is limited to 10 and the number of parts to 100. Larger, malformed, or unsupported messages cause an explicit error, not an apparently successful import. A parse/network error during retrieval does not save that batch. If a later database error occurs, earlier inserts in the batch may be retained; deduplication makes the next run safe.

    Protect access to emails, backups, and the CLI: messages may contain confidential data. Base64 is not encryption. Set your own retention period, restricted database permissions, and appropriate storage security. Incoming HTML is not sanitized: never render it directly in your application; display it as text with e() or use a separate, well-sanitized and protected viewer.

    Configuration

    System environment variables take precedence over .env. .env supports NAME=value, optional single/double quotes, and full-line comments. There is no interpolation, escape processing, multiline, or inline comment syntax. Use true/false for booleans. .env and database files are in .gitignore; new .env and SQLite files get Linux permissions 0600. On Windows, the folder's NTFS ACLs apply; restrict them in advance. APP_ENV accepts only local, testing, and production; a typo therefore does not silently disable production security.

    Production and Security Boundaries

    • Set the document root **only to public/**, never to the project root.
    • Use HTTPS, APP_ENV=production, and APP_DEBUG=false.
    • Behind an HTTPS reverse proxy, set SESSION_SECURE_COOKIE=true. The framework intentionally does not automatically trust forwarded headers.
    • Production refuses to start without HTTPS or explicit secure-cookie configuration. A secure cookie does not encrypt an HTTP connection: also enforce HTTPS in your web server or proxy.
    • Ensure PHP errors go only to protected server logs; also configure PHP itself with display_errors=Off and log_errors=On.
    • Give only the required user write access to the SQLite database, database directory, and storage/. On Linux, a file created with 0600 is readable only by its owner: align the CLI/PHP-FPM user accordingly. On Windows, restrict NTFS ACLs to the required users. Do not make the entire application writable by the web server.
    • Limit request sizes and timeouts in PHP and the web server; configure rate limiting and TLS/HSTS at the proxy or web server level.
    • Default headers include CSP, nosniff, frame blocking, a restricted permissions policy, and Cache-Control: no-store for application responses. The default CSP allows no scripts or inline styles; only the Swagger documentation gets the limited exception described above. Custom responses can explicitly change headers; keep such changes limited.
    • Static files are served directly by the web server: configure suitable caching and security headers for them yourself.
    • Protect custom routes with the auth guard and add per-object authorization and application-specific validation before public use.
    • Never run the development server as a production server. Security measures are not a guarantee: have a real application reviewed before deployment.

    Apache can use the included public/.htaccess with mod_rewrite and permitted overrides. For Nginx, configure PHP-FPM for /index.php only, deny hidden files, and use, for example:

    root /path/to/pbreeze/public;
index index.php;

location ~ /\. { deny all; }
location / { try_files $uri $uri/ /index.php?$query_string; }
location = /index.php {
    include fastcgi_params;
    fastcgi_param SCRIPT_FILENAME $document_root/index.php;
    fastcgi_pass unix:/run/php/php8.3-fpm.sock;
}
location ~ \.php$ { return 404; }

    Adjust the socket path for your installation and configure HTTPS separately. Never put confidential files or uploads containing executable code in public/.
